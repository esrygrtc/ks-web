one atomic checkpoint

Kill it anywhere. Resume anywhere. The world and the memory can never disagree.

A session is a micro-VM we can freeze. The freeze is one write, not three: if the filesystem were captured at t and the model memory at t plus 40 ms, the agent would wake remembering a file that does not exist.

Storage is content-addressed, so checkpointing every five minutes costs about 41 MB per freeze rather than a fresh 1.2 GB. That is why the cadence can be aggressive enough to make a crash boring.

$ ks run --image claude-code --checkpoint 5m
session s_7f3a started
$ kill -9 14203
$ ks resume s_7f3a
restored in 87s · nonce match · 0 bytes lost

Fork a two-day-old freeze ten times. The API is stateless; each fork is just a conversation that went differently. Your bill is the only one who notices, and a shared budget pool means a fan-out cannot exceed the cap you already set.

This is the difference between steering an agent and gambling on it. You stop choosing which instruction to try and run all of them from the same starting state, then keep the one that produced tests you believe.
